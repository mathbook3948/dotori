# 배포

dotori 실행 파일을 어떻게 만들어 사용자에게 내놓는지 정한다.

## 배경

dotori는 라이브러리가 아니라 PC에 설치하는 앱이다. 사용자가 Rust 도구 없이 받아서 쓸 수 있는 실행 파일이 필요하다.

## 내용

- 배포는 GitHub Release로만 한다. crates.io에는 올리지 않고, 모든 크레이트에 `publish = false`를 둔다.
- `v<버전>` 태그를 올리면 배포 워크플로가 돈다.
- 태그는 워크스페이스 버전과 같아야 하고, 다르면 릴리스를 만들지 않는다.
- 태그가 가리키는 커밋은 main에 있어야 하고, 아니면 릴리스를 만들지 않는다.
- 태그 검사는 어떤 빌드보다 먼저 한다.
- 빌드 전에 Linux, macOS, Windows에서 `mise run check`를 통과해야 한다.
- 워크플로를 손으로 돌릴 때도 같은 체크를 먼저 돌린다.
- Linux, macOS, Windows의 GitHub 기본 러너에서 각각 실행 파일을 빌드한다. 대상은 각 러너의 기본 아키텍처다.
- 압축 파일 하나에 실행 파일, README, 두 라이선스 파일을 넣는다.
- 압축 파일의 체크섬을 함께 올린다.
- 같은 태그의 릴리스가 이미 있으면 새로 만들지 않고 압축 파일과 체크섬을 덮어 올려서 멈춘 릴리스를 이어서 끝낸다.
- 같은 태그의 배포 실행은 동시에 돌지 않고 줄 서며, 대기 중인 실행을 취소하지 않는다.
- 릴리스 노트는 GitHub가 머지된 PR 제목으로 만든다. 따로 CHANGELOG를 두지 않는다.
- 워크플로를 손으로 돌리면 체크와 빌드와 체크섬까지만 하고 결과를 워크플로 아티팩트로 남긴다. 릴리스는 만들지 않는다.
- 실행 파일에 코드 서명과 공증을 하지 않는다. 사용자는 운영체제의 경고를 한 번 넘겨야 한다.

## 미정

- macOS 공증과 Windows 코드 서명.
- Intel Mac과 ARM Linux 같은 다른 아키텍처.
- Linux 실행 파일이 요구하는 glibc 범위와 deb 같은 패키지.
- 앱 안에서 새 버전을 알리거나 받는 방법.
